## 项目简报：远程控制 Cursor 解决方案优化

**项目背景：**

当前项目实现了一个通过手机远程控制桌面端 Cursor 应用的解决方案。该方案利用手机客户端发送指令，经由 Redis 的 Pub/Sub 机制传递给运行在用户 Mac 电脑上的 Node.js 服务器。服务器接收指令后，通过 AppleScript 驱动 Cursor 执行相应操作，并将执行结果通过 Redis 返回给手机客户端。

**当前痛点：**

现有架构依赖 Redis 服务器。为了使手机客户端能够与 Mac 上的 Redis 服务器通信，需要将 Redis 服务开通公网访问。这不仅增加了配置的复杂性，还带来了潜在的安全风险，如数据暴露、未授权访问等。

**提议解决方案：**

建议采用 Supabase 替换现有的 Redis Pub/Sub 通信机制，以解决公网访问和安全性的问题，并简化后端基础设施。Supabase 是一个开源的 Firebase 替代品，提供包括实时数据库、身份验证、存储和 Serverless Functions 在内的后端即服务 (BaaS) 功能。

**核心变更：**

1.  **数据通信迁移**：
    *   将使用 Supabase 的实时数据库功能替代 Redis Pub/Sub。
    *   创建两个核心数据表：
        *   `commands`：用于存储从手机客户端发送的指令，包含指令内容、状态（如待处理、处理中、已完成）、时间戳等。
        *   `results`：用于存储 Cursor 执行指令后的结果或错误信息，关联到相应的指令。
2.  **客户端改造**：
    *   手机客户端将不再直接与 Redis 通信，而是通过 Supabase SDK 将用户指令写入 `commands` 表。
    *   客户端将实时订阅 `results` 表或 `commands` 表的状态变更，以接收和展示 Cursor 的执行结果。
3.  **服务器端改造**：
    *   Node.js 服务器将移除 Redis 依赖，集成 Supabase SDK。
    *   服务器将实时订阅 `commands` 表中状态为"待处理"的新指令。
    *   接收到新指令后，服务器照常通过 AppleScript 控制 Cursor 执行。
    *   执行完毕后，将结果写入 `results` 表，并更新 `commands` 表中对应指令的状态。

**预期收益：**

*   **提升安全性**：无需直接将本地服务（如 Redis）暴露于公网。Supabase 提供了成熟的云端服务和安全机制，包括行级安全 (RLS)，可以精细控制数据访问权限。
*   **简化网络配置**：免去了配置 Redis 公网访问、防火墙规则、端口转发等复杂操作。
*   **结构化数据存储**：命令和结果将以结构化形式存储在 PostgreSQL 数据库中，便于查询、分析和历史追溯。
*   **利用 BaaS 功能**：未来可以方便地利用 Supabase 提供的其他后端服务，如用户身份验证、文件存储等，扩展项目功能。
*   **潜在成本优化**：Supabase 提供免费套餐，对于初期或中低流量项目可能更具成本效益。

**后续步骤建议：**

1.  **技术评估与原型验证**：搭建一个简单的原型，验证 Supabase 实时数据库在当前场景下的可行性和性能。
2.  **数据模型设计**：详细设计 `commands` 和 `results` 表的结构以及它们之间的关系。
3.  **安全策略规划**：定义 Supabase 的行级安全 (RLS) 策略，确保客户端和服务器端拥有恰当的数据访问权限。
4.  **代码迁移与重构**：逐步修改客户端和服务器端的代码，替换 Redis 相关逻辑为 Supabase SDK 调用。
5.  **测试与部署**：进行充分测试，确保新架构的稳定性和功能完整性后进行部署。

该方案旨在通过引入现代化的 BaaS 平台，优化项目架构，提升其安全性、可维护性和可扩展性。
